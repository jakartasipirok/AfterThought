From dataset to an approved graph

The model authors Python nodes. The supervisor executes those nodes and computes the evaluation.

Build and evaluate

  1. Freeze the dataset contractDeclare the binary target, positive label, permitted features, provenance and thresholds. Retain deterministic train/development/audit splits.
  2. Prepare a scoped workspaceStage training/development data, a profile, the graph interface and attributed memory. Load skill bodies on demand.
  3. Author fit and serve DAGsThe four-tool agent creates candidate.json and self-contained Python modules with run(inputs, config).
  4. Pin the candidateSnapshot source, trusted wrapper, runtime image, JSON config, bindings and limits into immutable revisions.
  5. Run and measureExecute fitting on training rows, then evaluate frozen serving predictions against retained development/audit labels and requested backtests.

Approve and serve

  1. Inspect the evidenceReview node source/configuration, model activity, evaluation gates, recall and false alarms.
  2. Record a human decisionThe operator clicks Approve and activate. A transaction validates eligibility and the expected active release, journals the reviewer, and updates the channel.
  3. Pin a batch to its releaseUpload a compatible serving CSV. Retain its input artifact and the approved graph/model identities.
  4. Execute the graphTemporal runs one Activity per node, in sequential topological order. Each node processes its batch using ordinary Python/ML computation.
  5. Retain outputs and signalsValidate row identities, probabilities, decisions and reasons. Store outputs, trace, usage counters and aggregate review signals.
Every activation is explicit. Evaluation creates an eligible candidate. The same-origin operator API records approval. An already admitted run retains its graph and fitted-model references through later activations.

Temporal owns durable orchestration

The client admits work, the service retains history, and a worker executes Workflow code and Activities.

Client

The Go API and CLI use the Temporal Go SDK. Request IDs and normalized input digests make repeated admission checkable. Identical requests reuse their identity; conflicting inputs fail.

Default task queue afterthought-agent-v1, configurable through AFTERTHOUGHT_TASK_QUEUE.

Service

Retains Workflow histories and dispatches Workflow/Activity tasks through the queue. Completed Activity results become replay inputs.

The local Compose deployment persists the Temporal development server's SQLite database in the temporal volume.

Worker

Polls the queue and registers six Workflows with their Activities. The default maximum concurrent Activity execution count is four.

The local maintenance loop runs about every 15 seconds to reap expired containers and dispatch/reconcile reviews.

Replay and retries

Workflow code is deterministic. Model calls, filesystem access, databases, Docker and wall-clock operations run inside Activities. Histories carry references and results, while large datasets/models live in artifact storage.

  • Model and tool Activities have one automatic execution attempt, a three-minute start-to-close timeout and a 15-second heartbeat timeout.
  • Graph-node Activities use the declared 1–3 attempts, node timeout plus 20 seconds, and a ten-second heartbeat timeout. Node Activities heartbeat every two seconds.
  • Committed node outputs are reused by invocation identity after a lost acknowledgement. An uncommitted node may execute again within its retry budget.

Failure semantics

  • A journaled completed tool call returns its cached result. An uncertain shell outcome is reported so the agent can inspect state.
  • An in-flight model/tool Activity can fail at timeout after worker loss because its automatic attempt budget is one. Completed Activity history remains available.
  • Batch completion and its unique signal are committed atomically. Retries preserve one counted batch.
  • Expected-current checks reject stale human approvals. Review dispatch uses stable IDs and reconciles retained Workflow/build status.
  • Recovery depends on retained histories, application records, artifacts, and available pinned images.

File tools and output validation

read, edit and write use a scoped os.Root. They reject traversal and special files, bound content, and require exactly one match for edits. Skill access uses a separate read-only root.

The trusted node wrapper serializes results. The host checks identity, protocol version, JSON shape, size and checksums before accepting output. Final predictions must cover every input row.

Operator and data boundary

The HTTP server binds to loopback. Mutations validate origin, and browser approvals require an exact same-origin request, reviewer identity and explicit decision. Keyed host clients are also supported.

The local application assumes a trusted operator. Permitted training/development content can be read by the agent, so selected features and prepared inputs determine model exposure. Audit data stays in supervisor storage. Public multi-user deployment needs authentication and stronger isolation.

State, artifacts and remembered evidence

Each store has a defined role in recovery, provenance and learning.

Application Postgres

Authoritative application records and transactional state. JSONB payloads retain graph/build metadata alongside relational identities and indexes.

Agent and admission journals

agent_api_requests, agent_sessions, agent_model_calls, agent_tool_calls retain input identities, session state, usage and tool outcomes. agent_memory holds attributed events and delivery receipts.

Dataset, release and execution state

agent_datasets, graph_builds, graph_releases, graph_channels, graph_approvals, graph_batches bind data contracts, candidates, active pointers, reviewer decisions and batch identities.

Review and policy state

graph_review_settings, graph_batch_signals, graph_auto_reviews, policy_documents, policy_channels, policy_proposals and policy_pattern_decisions retain review windows, proposals and policy versions.

Local content-addressed artifacts

.afterthought/ holds source packages, immutable dataset splits, transcripts, fitted model state, batch inputs, outputs, node commit records and scoped authoring workspaces.

Artifact references contain a SHA-256 digest and size. Graph/node identities bind their immutable execution inputs. Large content remains in this store while Temporal histories carry references.

Other durable stores

Temporal stores event histories in its own local SQLite volume. Hindsight persists its extracted memories in its service-owned database volume.

Preserve application Postgres, local artifacts, Temporal and Hindsight volumes together, plus access to pinned Docker images.

How Hindsight feeds the next revision

  1. Record the source eventPostgres retains execution measurements, failures, human feedback and model summaries with source attribution and deduplication keys.
  2. Deliver through the outboxStable document IDs and operation UUIDs make delivery retries repeatable. The outbox acknowledges acceptance while Hindsight processes asynchronously.
  3. Recall for authoringSetup combines recent journal evidence with task-scoped Hindsight recall and supporting source facts. Derived observations retain their uncertainty.
  4. Evaluate the resulting changeDevelopment evidence informs tuning. Original audit and benchmark reports remain with the supervisor/operator. Human approval and review outcomes become attributed evidence.

Node-level revision contract

Pin a parent release and choose fit:ID or serve:ID. Only the selected node's source/configuration may change. Packaging checks topology, bindings, limits and all protected revisions.

A fit-node change retrains the model. A serving-node change reuses the pinned fitted artifact. Compatible supplemental training/development partitions can accumulate for fitting. The original development/audit evaluation stays fixed.

Gates and interpretation

Demo gates require precision ≥50%, recall ≥30%, false-positive rate ≤50%, majority-baseline accuracy, and development F1 at least the parent's value. Original development/audit gates determine activation eligibility.

The data sequence is prepared; authored code and measured scores come from real execution. A completed rejected candidate can feed a later revision. Scores may rise or fall. The balanced benchmark differs from the original file's roughly 6% fraud prevalence.

Repeated comparison consumes holdout independence. Final generalization claims need fresh evaluation and verified target semantics.

Automatic proposals, human decisions

Auto-review is opt-in for a scope with an approved active graph. Enabling starts a fresh counter.

Collect

One finished serving CSV counts as one batch, including failed attempts once per request ID. Training and backtest jobs are excluded from this counter.

The worker checks about every 15 seconds and claims windows of 50. At five finished batches per minute, collection takes about ten minutes.

Choose the review

An attributable execution failure or invalid final output selects one serving node for repair. Runtime repair takes priority.

A fresh numeric departure can request a policy review. A healthy window records an observation. Review now consumes 1–50 available signals under existing guards.

Bound the attempt

One automatic authoring attempt, up to 12 model turns, a ten-minute cooldown, and one pending automatic proposal per parent release.

Task locks and a consumed sequence cursor coordinate concurrent completion and review claims. Existing pending work can delay another proposal.

Robustness repair

Give the author the affected node, sanitized aggregate diagnostics and attributed memory. Retain the triggering batch in supervisor storage.

Run original development/audit gates, enforce parent development F1, verify a changed selected node and successfully replay the failed batch. The eligible result waits for human activation.

Replay checks completion and prediction validity for that input. Accuracy on the repaired condition requires labelled evidence.

Policy and emerging-pattern review

Compare numeric batch values with frozen training ranges. Signals need at least ten training observations and at least three affected rows representing 10% of the batch, beyond the configured margin.

The agent proposes an investigator procedure with policy-page quotations and observed evidence IDs. Missing knowledge pauses at needs_policy. A human assesses the hypothesis and approves or dismisses the amendment.

The guided policy controller requests a serving-output-node revision after publication. Graph evaluation and a separate human approval precede activation.

Numerical detector and PDF limits

The departure margin is max(25% of training range, 1% of absolute maximum, 0.01). Detection covers numeric range departures. Categorical novelty, correlations and label-based accuracy need additional analysis. Reviewed dataset/feature/direction signatures are suppressed for the current policy version.

Poppler extracts searchable PDFs with limits of 8 MiB input, 30 pages, 128 KiB text and 20 seconds. Versioned numbered policy pages are staged in knowledge/company-policy.json. Proposal validation checks bounded fields, exact whitespace-normalized page quotations and observed evidence references.

Contracts at the system boundaries

Explicit data and graph interfaces let the supervisor validate independently of the agent's summary.

Dataset and node interface

Headered CSV, binary target, at least 50 rows and ten rows per class. Limits are 64 MiB, 100,000 rows, 128 source columns, 64 selected features and 16 KiB per cell.

Feature types are inferred as numbers, booleans, strings and nullable values. Supplemental datasets share scope, label mapping and ordered feature types. Evaluation-only data is reserved for backtests.

candidate.json · version v2
  fit   → at least one node
  serve → at least two connected nodes
  each graph → at most 16 nodes

run(inputs, config) → JSON result
bindings → $input / predecessor / $fit

Each node declares source, dependencies, bindings, config, timeout and attempts. Fitted state flows through the fit artifact.

Serving output

{
  "predictions": [{
    "row_id": "claim-row-id",
    "probability": 0.72,
    "decision": "escalate",
    "reasons": [
      "Request an independent repair estimate."
    ]
  }]
}

Require one prediction per input row, matching IDs, finite probabilities in [0, 1], a supported accept/escalate/reject decision, and nonempty reasons.

Metrics use probabilities at the frozen threshold. Human review assesses the business meaning of reasons and recommendations.

Coverage includes graph execution, dataset isolation, cumulative learning, approval rejection, retry identities, history replay and automatic-review gates. Integration tests require local services and runtime images.

The implementation targets local binary tabular classification. Follow-on work includes authenticated shared access, distributed artifacts/images, entity/time split policies, final-audit rotation and richer drift/verified-feedback triggers.
